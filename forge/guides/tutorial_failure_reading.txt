# tutorial-failure-reading

## SUMMARY
Learn how to read failed or skipped Forge packets and choose the next safe move.

## WHEN TO USE
Use this when a run has FAILED, FAILED_PARSE, SKIPPED, anchor mismatch, core guard, or confusing output.

## GOAL
Learn the response pattern:

1. Read the summary.
2. Find failed and skipped ops.
3. Read the exact reason.
4. Use HELP for syntax errors.
5. PREVIEW before retrying patches.
6. Do less in the next bundle.

## FIRST RULE
The packet is truth.

If a packet says FAILED, that op did not complete.

If a packet says SKIPPED, it did not apply a new change.

If a packet says APPLIED, Forge performed that op — but you may still need to verify behaviour with RUN_FILE or PREVIEW.

## STEP 1 — READ HELP FOR COMMON FAILURES
This bundle opens HELP for common ops involved in failed packets.

    @forge-bundle tutorial-failure-help
    HELP GREP

    HELP PREVIEW

    HELP REPLACE_LINES

    HELP REPLACE_FILE_RANGE

    HELP BRANCH

    DOCS
    SUGGEST: run-packet, safe-patch, inspect-first
    @end-forge-bundle

## EXPECT
The packet should show exact syntax and common failures.

Use HELP before retrying after FAILED_PARSE.

## FAILED_PARSE
FAILED_PARSE usually means the bundle syntax was wrong.

Common causes:
- wrong directive name
- missing required directive
- body where body is forbidden
- malformed line range
- unclosed body fence

Safe response:

    HELP <OP>
    PREVIEW the target if needed
    retry with a smaller bundle

## MISSING DIRECTIVE
If the packet says something like:

    GREP missing PATTERN

Then the fix is usually direct:

    HELP GREP

Then retry with PATTERN.

Example:

    @forge-bundle tutorial-failure-grep-correct
    GREP .
    PATTERN: tutorial
    EXT: .txt
    LIMIT: 20
    @end-forge-bundle

## INVALID DIRECTIVE
If the packet says a directive is not allowed, remove it or use the right op.

Examples from real audits:
- GREP does not use MODE
- GREP uses PATTERN, not PATH
- PREVIEW does not use TARGET
- REPLACE_FILE_RANGE uses LINES
- REPLACE_LINES uses ANCHOR_START and ANCHOR_END

Safe response:

    HELP <OP>

Do not guess.

## SKIPPED_ANCHOR_MISMATCH
This means an anchor matched zero times or too many times.

The patch did not apply.

Safe response:

1. PREVIEW the target.
2. Copy the exact current text.
3. Tighten the anchor.
4. Retry smaller.

Useful bundle:

    @forge-bundle tutorial-failure-preview-before-retry
    PREVIEW forge/guides/tutorial.txt
    LINES: 1-80
    @end-forge-bundle

## FAILED_COMPILE
This means Forge applied a Python patch, then compile() failed.

Forge rolls the file back automatically.

Safe response:
- read the traceback
- inspect the target
- retry with a smaller patch
- run the file again after fixing

## CORE GUARD
Core guard protects important Forge files.

If you hit core guard, do not fight it.

Safe response:
- create a BRANCH first
- keep the patch tiny
- test with RUN_FILE
- know how to recover

Read [[core-edit]] before touching core files.

## FAILED_IO
FAILED_IO usually means:
- file not found
- directory not found
- path typo
- target escaped project root

Safe response:

    LIST_FILES .
    DEPTH: 2
    FILES: no

Then narrow from there.

## BAD RETRY PATTERN
Do not do this:

1. Send big bundle.
2. It fails.
3. Send another big bundle.
4. Guess syntax.
5. Patch without previewing.

That creates noise and risk.

## GOOD RETRY PATTERN
Do this:

1. Read the failed line.
2. Run HELP for that op.
3. PREVIEW the target.
4. Retry only the failed part.
5. Add DOCS SUGGEST for useful docs.

## USEFUL RECOVERY BUNDLE
When confused, this is a good read-only reset.

    @forge-bundle tutorial-failure-reset-context
    LIST_RUNS

    DOCS
    OPEN: run-packet
    SUGGEST: safe-patch, inspect-first, tutorial-recovery
    @end-forge-bundle

## WHAT YOU LEARNED
You learned how to slow down after failure.

The rule is:

    HELP after FAILED_PARSE.
    PREVIEW after anchor mismatch.
    DIFF before revert.
    BRANCH before risk.
    Smaller bundle after failure.
