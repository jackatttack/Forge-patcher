# core-edit

## WHEN TO USE
Use when touching Forge files that can break parsing, execution, registry, packets, safety, or the Shortcut entry path.

Examples:
- forge/bridge.py
- forge/parser_main.py
- forge/engine.py
- forge/registry.py
- forge/run_packet.py
- forge/validators.py
- forge/core_guard.py
- forge/compat_normalizer.py
- forge_entry.py

## PATTERN
1. Create a BRANCH first.
2. Keep the batch small.
3. Do not combine core edits with unrelated app work.
4. Prefer whole-function replacement over fragile nested line-range edits.
5. Add CONFIRM: yes when core guard requires it.
6. REFRESH.
7. RUN_FILE forge/entry.py.
8. Test the specific behaviour that changed.

## GOOD FIRST MOVES
- BRANCH create before_core_change with the files you may touch.
- PREVIEW the core file.
- LIST_TARGETS if it is Python and you need a target name.
- HELP the write op before patching.

## VALIDATE / SMOKE TEST
Minimum:
- REFRESH
- RUN_FILE forge/entry.py

Then test the changed behaviour directly.

## RECOVERY
Branches include standalone restore scripts at forge/artifacts/branches/<name>/restore_branch.py.

If Forge breaks badly, run the restore script directly in Pythonista.

## COMMON FAILURES
- Syntax error in bridge/parser/engine can break Forge entry.
- Line-range edits inside nested control flow are risky.
- New ops may need REFRESH or a Pythonista restart before parser recognition.
- If core guard blocks an edit, branch first and retry with CONFIRM: yes.
