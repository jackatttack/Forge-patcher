# ui-house-style

SUMMARY: Use when building Jack-style first-class Pythonista UIs: dark, compact, card-based, chip-driven, fast under real work pressure.

## WHEN TO USE

Use when designing or refreshing a first-class UI for one of Jack's tools:
- Journal
- PDF Library Console
- Forge surfaces
- Maths tools
- Flashcards
- Sheets/views
- lesson/work dashboards
- any CLI-backed app that has become important enough to deserve a polished interface

Use this alongside:
- GUIDE first-class-ui for the workflow of turning a proven engine/CLI into a UI
- GUIDE safe-patch for making ordinary code changes safely
- GUIDE inspect-first before entering unfamiliar files

## CORE PRINCIPLE

The house style is not decoration first.

It is:
- fast
- compact
- dark
- readable
- practical
- action-forward
- useful under pressure

Design for Jack using the app while doing real work: tutoring, teaching, coding, managing projects, or quickly surfacing information.

The UI should reduce cognitive load, not add theatre.

## VISUAL LANGUAGE

Prefer:
- dark background
- muted panels
- rounded cards
- clear accent colour
- compact chips/pills
- strong but restrained hierarchy
- minimal borders
- high contrast text
- small labels for metadata
- bold titles for what matters
- action buttons that are obvious but not noisy

Typical palette direction:
- app background: near black / dark charcoal
- cards: slightly lighter charcoal or dark blue-purple
- borders: subtle dark grey / purple-grey
- primary text: off-white
- secondary text: muted grey
- accent: soft indigo/purple
- warning/action accent: warm yellow/orange
- success: muted green

The feel should be closer to Journal/PDF Console than to default iOS forms.

## LAYOUT PRINCIPLES

Use cards for meaningful grouped work:
- Stitch / Quick Pack panel
- result cards
- entry previews
- workflow panels
- editor overlays

Use chip rows for fast filtering:
- source/type
- kind
- exam tier
- paper number
- tags
- status
- quick intents

Use dense scrollable results:
- results should become the main thing once the user has searched
- avoid wasting vertical space on static titles
- allow top controls to collapse/minimise after the user is in browsing mode

Fullscreen is usually right for core tools.

Use hide_title_bar=True when the app has its own header or when maximum space matters.

## INTERACTION PRINCIPLES

Typing should live-filter.

Source/type chips should be hard constraints:
- if Corbett is selected, only Corbett results should appear
- if Papers is selected, worksheet results should not leak in unless explicitly intended
- if a tier/paper filter is selected, results should honour it

Tag chips are discovery tools:
- update tag suggestions while typing
- use fuzzy matching for typos
- tap tag chips to add useful terms/search constraints
- keep tags visible enough to teach the user what vocabulary exists

High-value actions should be first-class:
- Open
- Share
- Stack
- Stitch
- Build + View
- Build + Share
- Edit tags
- Collapse controls

Do not bury the main workflow in a settings panel.

## LIVE-USE RULES

Design for distracted use.

Jack may be:
- mid-lesson
- using a phone one-handed
- moving between phone and iPad
- trying to answer a student's request quickly
- under time pressure
- typing imperfectly

Therefore:
- labels should use Jack's language
- fuzzy search is valuable
- share/export must be obvious when device handoff matters
- keyboard must not hide the useful results
- results should stay visible while typing
- control panels should collapse when browsing
- tap targets need to be comfortable
- state should be preserved when collapsing/expanding

## COMPONENT PATTERNS

### Header

Use a compact custom header if needed:
- title
- small subtitle
- optional status/summary

Avoid a native title bar if it wastes space.

### Search box

Use high-contrast input:
- dark surrounding UI is fine
- text field itself may be white with black text if readability wins
- live-filter on change
- disable autocorrect/autocapitalisation for tags/code/search terms unless prose input is intended

### Chips

Use horizontal scroll rows:
- selected chip: accent background, white text
- unselected chip: muted dark background, muted text
- source/mode chips above topic chips
- exam/status chips separate from topic tags when helpful

### Cards

A card should answer quickly:
- what is this?
- what type/source is it?
- why did it match?
- what can I do with it?

Good card structure:
- badge/source line
- title
- small metadata
- tags
- action buttons

### Collapsed Controls

Once a search/filter is set, offer a compact mode:
- hide stitch/search/filter panels
- show a small summary bar
- keep result list dominant
- allow one tap to expand controls again

Summary should include:
- query
- active source/mode
- key filters
- result count

## PYTHONISTA IMPLEMENTATION NOTES

Pythonista UI has quirks:
- some ui classes cannot be subclassed safely, including ui.Button
- use wrapper/composition objects for reusable controls
- test with RUN_FILE after small patches
- run packets prove launch, but Jack's visible feedback proves UI correctness
- avoid over-bundling UI patches
- after a failed patch, recover the app to running before continuing

For share/export:
- console.open_in(path) opens the iOS share sheet
- this is first-class when Jack moves files from iPhone to iPad

For document/PDF tools:
- native Pythonista UI is often best for control surfaces
- ui.WebView is good for rendering PDFs or rich HTML views
- reuse proven viewers before rebuilding rendering

## DO

Do:
- preserve the user's current state
- make filters visibly active
- make results dominate after search
- use collapsed modes
- use fuzzy matching where typos are likely
- make sharing/export obvious
- keep common actions one tap away
- use Jack's words for important actions

Examples:
- use "Stitch" if Jack thinks of the workflow as Stitch
- use "Build + Share" when the point is creating a pack and sending it onward
- use "Stack visible" when the action opens the current visible result set

## DON'T

Do not:
- waste screen space with redundant title bars
- rely on generic iOS form styling for first-class tools
- make Jack type command syntax inside a UI
- hide the main workflow behind a gear/settings button
- let filters behave as loose suggestions when they look like constraints
- make management tools before the live-use workflow is excellent
- over-style at the cost of speed or clarity
- let old prototype UI dictate the final product

## VALIDATE

For every UI pass, check:
- Does it launch?
- Can Jack complete the main workflow in a few taps?
- Does typing update results?
- Do chips behave as hard constraints where expected?
- Are results visible with keyboard open?
- Can controls collapse when browsing?
- Does sharing/export work?
- Is the screen mostly useful content, not chrome?

For live-use tools, ask Jack for visible feedback after RUN_FILE.

## LESSON: FIRST-CLASS PANEL VIEWS

For serious Pythonista tools, prefer reusable panel views over ad-hoc overlays.

A strong panel should usually be its own `ui.View` class with:
- `_build()` for static controls
- `layout()` for geometry
- `show()` / `open()` for entry
- `close()` for exit
- callbacks such as `on_close`, `on_select`, `on_add`, `on_state_change`
- no dependency on fragile module globals
- parent-owned orchestration when multiple panels can conflict

Good examples from Forge Run Centre:
- `SideDrawer` for workspace tools
- `PacketDrawer` for console/output/run feedback
- `RunHistoryPanel` for previous packets and recovery actions
- `CommandLibraryPanel` for Help/Guide surfacing
- `FilePicker` and `FileViewer` for inspection workflows
- `ClipboardPanel` for clipboard-driven feedback loops
- `AddOpPanel` for structured bundle creation

Panel views should be button-first. Gestures are allowed only as secondary affordances once they are proven reliable. If a gesture interferes with normal app use, suppress it or remove it.

Use panels when a feature has its own state, search/filtering, scroll area, or multi-step interaction. Do not cram this kind of workflow into the main view or a tiny popover.

When panels can overlap or fight, the parent app should own mutual exclusion:
- opening the right packet drawer should close/suppress the left tools drawer
- opening a full-screen picker should suppress edge gestures
- drawer gestures should only be enabled on the main run surface
- a reliable button should always exist as a fallback

This pattern is now part of the Forge/Pythonista house style: main workspace stays clean, specialist surfaces slide or reveal in, and the app remains recoverable even if gestures are imperfect.
