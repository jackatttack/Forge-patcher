# system-health

SUMMARY: Use when Jack wants a Forge/system health pass: combine audit ops, recent run history, and honest session review to decide what to tighten next.

## WHEN TO USE

Use when Jack asks for:
- a Forge audit
- system health
- review of a Forge session
- what was strong and worth building on
- what was weak and should be tightened
- whether HELP, GUIDE, compat hints, normalisers, audit ops, or run packets need improvement

This is not only a static code audit.

System health means checking:
- Forge's static op/help surface
- real behavioural failures from recent runs
- model mistakes during the session
- recovery quality
- whether repeatable lessons deserve GUIDE/HELP/compat updates

## CORE IDEA

Run the tools, then think.

Do not write a health guide, compat rule, or normaliser from vibes alone. Use real signals first.

## GOOD FIRST MOVES

Read the existing health workflows:

GUIDE
ARGS: forge-health

GUIDE
ARGS: compat-learning

Then run the audit surfaces:

FORGE_AUDIT

COMPAT_AUDIT

LIST_RUNS

If needed:

HELP FORGE_AUDIT

HELP COMPAT_AUDIT

HELP LIST_RUNS

Use LIST_OPS custom or LIST_OPS all only if unsure what health tools exist.

## HOW TO READ THE TOOLS

### FORGE_AUDIT

Static/system health.

Read buckets differently:
- ISSUES: reliability problems; usually fix soon
- WARNINGS: drift or missing guidance; important
- POLISH: documentation/help/hints debt; useful but not blocking
- NOTES: optional observations

A healthy result can still have polish debt.

### COMPAT_AUDIT

Behavioural/run-history health.

Look for:
- repeated FAILED_PARSE patterns
- skipped anchor mismatches
- invalid directives
- missing directives
- normalisations
- core guard hits
- repeated weird internal errors
- learn candidates

Do not overreact to one-off mistakes.

### LIST_RUNS

Recent session trail.

Use it to see:
- whether failures clustered around one file/task
- whether recovery happened cleanly
- whether large bundles caused partial state
- which runs are worth inspecting further

## SESSION REVIEW

After running the tools, review the actual conversation/run packets.

Look for:
- Did the model inspect before patching?
- Did it use HELP/GUIDE when appropriate?
- Were patches too large?
- Did failures produce useful diagnostics?
- Did recovery happen quickly?
- Did any mistake recur?
- Was the user forced to steer around avoidable model behaviour?
- Did the session reveal a repeatable workflow worth saving?

Also capture what worked:
- additive files
- small safe patches
- model layer before UI
- run packets as truth
- GUIDE updates after patterns emerged
- clean recovery after failed patches

## CLASSIFY FINDINGS

Use these buckets.

### Strong / build on

Things that worked and should become standard.

Examples:
- audit split: FORGE_AUDIT + COMPAT_AUDIT + LIST_RUNS
- additive files before mutation
- small patches after drift starts
- GUIDE before future builds
- model/service layer before UI shell

### Weak / tighten

Things that caused friction.

Examples:
- over-bundled patches
- wrong directives
- unclear internal errors
- missing HELP/HINTS on recovery ops
- repeated anchor mismatch
- model guessed instead of inspecting

### System improvement candidates

Changes that might deserve work.

Examples:
- update HELP
- add HINTS
- add or append GUIDE
- improve compat_hints.py
- add safe normaliser
- improve audit output
- improve run packet suggestions
- create a custom op

### Not worth systemising

One-off weirdness or low-value trivia.

Do not turn every mistake into process.

## DECISION RULES

Update GUIDE when:
- a workflow succeeded and is likely to recur
- Jack explicitly says a pattern matters
- future models would save time by reading it
- the issue involves judgement/process rather than one op's syntax

Update HELP when:
- the problem is concrete op usage
- examples or directive docs would prevent the mistake
- the op is important during recovery or common workflows

Update HINTS / compat hints when:
- the model made a clear near-miss
- the intent was obvious
- the failure is likely to recur
- teaching recovery is safer than normalising

Add a normaliser only when:
- the miss is deterministic
- common enough to justify it
- unambiguous
- safe

Create a custom op only when:
- the workflow is stable
- inputs/outputs are clear
- it should become first-class in LIST_OPS custom

Keep as guide when:
- the workflow requires judgement
- it combines audits, session review, and prioritisation
- the output is a recommendation rather than a mechanical command

## OUTPUT FORMAT

A useful system-health response should include:

### Health summary
Short judgement: healthy, warning signs, or needs work.

### Strong / build on
Concrete things that worked.

### Weak / tighten
Concrete mistakes or friction.

### Audit signals
What FORGE_AUDIT, COMPAT_AUDIT, and LIST_RUNS showed.

### Recommended fixes
Prioritised:
1. immediate low-risk fix
2. guide/help/hint improvement
3. larger structural idea, only if justified

### Suggested bundle
Only if useful. Prefer small targeted bundles.

## COMMON FAILURES

Do not:
- write the guide before testing the flow
- only run audits and ignore the actual session
- only reflect emotionally and ignore audit data
- over-systemise one-off mistakes
- mutate Forge before reading health signals
- combine health work with unrelated product work
- give vague praise without naming what specifically worked
- add normalisers just because a mistake happened once

## VALIDATE

A good health pass should leave one of:
- clear no-action-needed conclusion
- journal entry
- guide update
- HELP/HINTS improvement
- small targeted patch
- prioritised next-step list

It should not end with vague “we should improve things”.
