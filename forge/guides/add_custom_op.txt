# add-custom-op

## WHEN TO USE
Use when a repeated workflow deserves to become a first-class Forge command.

Good candidates:
- CLI wrappers Jack will use often
- read-only audits
- integrations
- prompt-card / mode-card ops
- project-specific tools
- workflows that should show up in LIST_OPS custom

## PATTERN
1. Inspect a similar existing op.
2. Create a file in forge/ops/custom.
3. Include SPEC, HELP, HINTS, validate, and execute.
4. Keep validation strict and messages useful.
5. Add a CLI main if RUN_FILE testing would help before parser recognition.
6. REFRESH.
7. LIST_OPS custom.
8. HELP the new op.
9. Test one real command.

## GOOD FIRST MOVES
- LIST_FILES forge/ops/custom
- PREVIEW a similar op
- HELP FORGE_AUDIT
- GUIDE core-edit if the op touches Forge internals

## REQUIRED SHAPE
Every op should have:
- SPEC: name, target_kind, body_mode, allowed_directives, required_directives
- HELP: summary, safe usage, examples, related ops
- HINTS: useful recovery hints where relevant
- validate(parsed_op)
- execute(ctx, parsed_op, result)

## VALIDATE / SMOKE TEST
After creating or editing an op:
- REFRESH
- LIST_OPS custom
- HELP NEW_OP
- Run the op with a tiny command
- Consider FORGE_AUDIT if the op is important

## COMMON FAILURES
- Brand-new ops may need one restart before parser recognition.
- Missing or weak HELP makes the op harder for future models.
- sys.exit inside a RUN_FILE-tested op module can look like failure in Pythonista.
- allowed_directives and required_directives should usually be sets unless deliberately allowing any directives.
