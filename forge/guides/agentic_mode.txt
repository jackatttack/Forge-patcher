# agentic-mode

SUMMARY: Use when Jack wants a tight build loop: issue bundles, read packets, continue automatically until the stated goal is achieved or a real stop condition appears.

## WHEN TO USE

Use when Jack explicitly asks for momentum rather than discussion.

Trigger phrases may include:
- agentic mode
- crack on
- tight loop
- keep going until it works
- get on with it
- run the loop
- drive this one
- do the work, I will send packets back

This guide changes model behaviour. It is not just an implementation recipe.

Normal mode is conversational: discuss, explain, ask, design, then patch.

Agentic mode is execution-led: inspect, patch, test, read packet, continue.

## CORE PRINCIPLE

In agentic mode, convert observations into the next useful bundle.

Do not pause after every packet to explain broadly.
Do not ask “what next?” when the next step is obvious.
Do not write long commentary unless a decision, danger, or product judgement is required.

Jack provides the run packet.
The packet is truth.
The model drives the next bundle.

## LOOP

1. Restate the goal briefly if useful.
2. Load only the guides/context needed for the task.
3. Inspect before writing.
4. Create one branch before meaningful file changes.
5. Patch in small recoverable steps.
6. Smoke test.
7. Read the packet.
8. Continue with the next bundle.
9. Stop only when the goal is achieved or a stop condition appears.
10. Add a checkpoint/journal entry when the work is meaningful.

Typical loop:

  inspect -> branch -> patch -> refresh/test -> packet -> patch -> test -> checkpoint

## RESPONSE STYLE

Keep prose short.

Good:

  Landed. Next I am testing the new path.

  <bundle>

Good:

  Anchor drift. Inspecting the exact region now.

  <bundle>

Good:

  Core file involved. Creating one branch, then patching only the validator.

  <bundle>

Bad:

  Long explanation of every possible approach before doing the next obvious step.

Bad:

  Asking Jack what to do next when the packet already shows the next action.

Bad:

  Repeating guide content back to Jack instead of acting on it.

## FIRST MOVES

For app/UI work:
- GUIDE inspect-first
- GUIDE safe-patch
- GUIDE ui-house-style
- relevant LIST_FILES / LIST_TARGETS / PREVIEW

For Forge internals:
- GUIDE core-edit
- GUIDE forge-health
- GUIDE compat-learning when failures/normalisers/hints are involved
- HELP relevant ops before unfamiliar syntax

For guide/help/docs work:
- GUIDE guide
- PREVIEW existing nearby guide
- CREATE_FILE or REPLACE_FILE_LINES

Do not load every guide. Load the smallest useful set.

## BRANCHING

Create one branch before meaningful edits.

Good:
- one branch before a coherent build chunk
- branch all files likely to be touched
- branch before Forge core/parser/registry/engine changes
- branch before risky UI refactors

Avoid:
- creating a new branch for every tiny patch
- branching after the risky edit has already happened
- mixing unrelated work into the same branch/checkpoint

If the task changes substantially, create a new branch.

## PATCH SIZE

Prefer small, recoverable bundles.

A good agentic bundle usually does one of:
- inspect one area
- patch one behaviour
- repair one failure
- run one smoke test
- add one guide/checkpoint
- audit one class of problem

Do not batch broad unrelated edits just because the mode is faster.

## PACKET HANDLING

After each packet:

If APPLIED and tests pass:
- continue to the next useful step.

If FAILED_PARSE:
- run HELP for the failed op or fix obvious syntax immediately.
- do not retry by guessing unsupported directives.

If SKIPPED_ANCHOR_MISMATCH:
- use the packet suggested previews.
- tighten anchors.
- use OCCURRENCE only after confirming repeated structure.
- use REPLACE_FILE_RANGE only after line numbers were just previewed.

If FAILED_COMPILE or import break:
- repair the broken file before continuing.
- use branch restore if repair is not obvious.

If FAILED_CORE_GUARD:
- follow GUIDE core-edit.
- branch first.
- isolate the core edit.
- add CONFIRM: yes only when the branch exists and the edit is intentional.

If UI launches but visual correctness matters:
- ask Jack for visible feedback or screenshot only when needed.
- do not keep blindly polishing a visual issue without device feedback.

## STOP CONDITIONS

Stop the loop when:
- the stated goal is achieved
- safety risk appears
- the app/import is broken and restoration decision is needed
- repeated failures suggest the current plan is wrong
- visual UI feedback from Jack is required
- the next step is product judgement, not implementation
- a destructive action needs explicit confirmation
- the work crosses into a new scope

When stopping, say why and give the next best bundle or checkpoint if appropriate.

## SAFETY

Never use agentic mode as permission to be reckless.

Do:
- inspect before patching
- branch before meaningful writes
- keep changes scoped
- run smoke tests
- trust packets over assumptions
- repair breakages immediately
- keep destructive actions explicit

Do not:
- delete files without confirmation
- touch unrelated files
- patch core Forge files casually
- ignore failed imports
- continue after a broken app without repair
- use broad line-range edits without preview
- hide uncertainty

## JOURNAL / MEMORY

At the end of a meaningful agentic session:
- add a concise journal progress entry
- add an llm-reflect entry if the workflow taught something reusable
- use MEMORY only when the session changes durable continuity

Good checkpoint:
- what shipped
- files touched
- tests run
- current state
- open threads
- safest next step
