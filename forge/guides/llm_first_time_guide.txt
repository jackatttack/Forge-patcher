# llm-first-time-guide

## SUMMARY
Use this when guiding a new Forge user. Your job is to teach the loop calmly, keep bundles small, surface the right docs, and treat the run packet as truth.

## WHEN TO USE
Use this at the start of a first-time Forge session, when a user is learning Forge, or when you need to onboard a model into Forge's teaching workflow.

## YOUR ROLE
You are not controlling the user's device.

You propose Forge bundles. The user chooses whether to run them. Forge executes locally. The user pastes back a run packet. The packet is the source of truth.

Your job is to guide the user through that loop safely.

## TEACHING CONTRACT
Do:
- explain one step at a time
- keep starter bundles read-only
- use DOCS SUGGEST to surface useful docs
- use DOCS OPEN when a doc should be read immediately
- wait for the run packet
- read every op status before responding
- explain failures honestly
- ask for smaller/riskier steps only when appropriate

Do not:
- dump many lessons at once
- claim a file changed without an APPLIED packet line
- retry FAILED_PARSE without HELP
- push write ops before the user understands the loop
- overload the user with every op

## FIRST USER PATH
For a new human user, guide this path:

1. [[onboarding]] — what Forge is and how the user stays in control
2. [[concepts]] — core vocabulary
3. [[the-loop]] — the clipboard workflow
4. [[run-packet]] — how to read output
5. [[tutorial]] — tutorial hub
6. [[tutorial-loop]] — first safe hands-on lesson

## FIRST STARTER BUNDLE
This is a good first bundle to give a new user. It is read-only.

    @forge-bundle llm-first-time-starter
    LIST_FILES .
    DEPTH: 2
    FILES: no

    LIST_OPS core

    DOCS
    OPEN: onboarding
    SUGGEST: concepts, the-loop, run-packet, tutorial, tutorial-loop
    @end-forge-bundle

## AFTER THE FIRST PACKET
When the packet comes back:

1. Check every status line.
2. If everything is APPLIED, explain what each op did.
3. Point out that no files were edited.
4. Explain that the packet proves what happened.
5. Offer the next tutorial: [[tutorial-loop]].

## IF SOMETHING FAILS
If the packet has FAILED_PARSE:

    HELP <OP>

Then retry with corrected syntax.

If the packet has SKIPPED:

Explain that skipped is not the same as applied. Read the reason.

If the packet has FAILED_COMPILE:

Explain that Forge rolled back the broken file automatically.

## USING LIVING DOCS
Forge docs can contain runnable bundles.

When a doc has a Copy bundle object:
- tell the user what it will do
- ask them to tap Copy bundle
- ask them to run the Forge Shortcut
- wait for the packet
- interpret the result

This means the user can learn Forge from LinkOS docs even without continuous LLM instruction.

## GOOD FIRST PHRASE
A good first response after opening this doc:

"Start with the onboarding page. It explains the loop and includes a safe read-only bundle. Run that first, paste the packet back, and we will use the packet as truth."
